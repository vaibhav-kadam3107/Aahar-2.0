# Aahar 2.0 - AI Food & Macro Tracker Backend

Aahar 2.0 is a serverless, database-backed personal health application featuring AI-powered food photo analysis and real-time nutrition coaching. The backend is built on the [InsForge BaaS](https://insforge.dev) platform, leveraging a PostgreSQL database, secure file storage, Row-Level Security (RLS) policies, and Deno Edge Functions integrated with Gemini AI.

## 1. Completed Tasks & Backend Details

### Database Schema (`schema.sql`)
The database contains 5 core tables fully configured with custom indexes and Row-Level Security (RLS) policies to isolate data per user:

*   **`profile`**: Holds user goal metrics (`height_cm`, `weight_kg`, `age`, `gender`, and daily calorie/macronutrient goals). Primary key is `user_id`, referencing `auth.users(id)`.
*   **`meals`**: Logs meal sessions with photo paths, meal classifications (Breakfast/Lunch/Snack/Dinner), overall calories, protein, carbs, fat, fiber, micronutrient JSON structures, and an `idempotency_key`.
*   **`meal_food_items`**: Contains portion estimates and specific macro splits for individual ingredients detected within a single meal. Referenced to `meals.id`.
*   **`coach_messages`**: Logs historical coach-user dialogues to maintain conversation context.
*   **`weight_logs`**: Timed entries for tracking weight fluctuations.

#### Security & Indexing
*   **Indexes**: Created B-Tree indexes on all foreign key lookups (`user_id` and `meal_id`) and timestamp columns (`consumed_at`, `logged_at`, `created_at`) to ensure database queries utilize index scans rather than full table scans.
*   **Row-Level Security (RLS)**: Enabled RLS on all tables. Applied policies enforcing `user_id = auth.uid()` for all CRUD operations, ensuring users can only read and write their own data. For `meal_food_items`, access is governed by checking if the referenced meal belongs to `auth.uid()`.

### Private Storage Buckets
Created a private bucket named `meals` to store food photos uploaded by the client application. Direct public access is disabled (`Public: No`); objects are retrieved exclusively via temporary signed download URLs generated by the storage provider.

### Edge Functions
Deployed two serverless edge functions inside InsForge running on Deno:

1.  **`analyze-meal`**:
    *   Verifies user session authenticity via `/api/auth/sessions/current` using the forwarded token.
    *   Enforces an **idempotency check** against the database using `idempotency_key` (if matched, returns the existing meal and food breakdown immediately, preventing duplicate API calls).
    *   Enforces a **rate-limiting guard** limiting users to a maximum of 20 meal analysis requests per 24 hours.
    *   Downloads the uploaded image, checks that it is under **2MB**, encodes it in base64, and prompts `gemini-3.6-flash` (our primary active model) with a structured prompt.
    *   Validates the structured JSON returned by Gemini, performs an atomic database insert into `meals` and `meal_food_items` using direct REST calls with `Prefer: return=representation` headers, and returns the parsed result with the signed image URL.
    *   Includes exponential backoff (1s then 3s, max 2 retries) on transient Gemini failures.
2.  **`coach-chat`**:
    *   Maintains a low context overhead by retrieving only meals logged in the last 7 days and computing a compact average daily macronutrient summary.
    *   Loads only the last 6 conversation turns from `coach_messages`.
    *   Prompts `gemini-3.6-flash` with the history, stats summary, and new message, storing both the user prompt and AI response to the database before returning.

## 2. E2E Architecture & Flow Connection

The frontend connects directly to the InsForge REST API gateway and serverless function endpoint:

```
[HTML Frontend Client]
       │
       ├─► (HTTPS/REST) Auth API (Token generation & Session checks)
       ├─► (HTTPS/REST) Storage API (Upload/Download strategies + S3 Upload)
       ├─► (HTTPS/REST) Database API (Direct CRUD on Profile/Weight logs)
       └─► (HTTPS/REST) Edge Functions (Analyze-meal & Coach-chat calls)
```

### Flow 1: Session Initialization (Anonymous MVP Auth)
To support a zero-friction test environment, the frontend automatically implements an anonymous authentication flow:
1.  On load, the client checks `localStorage` for a saved session.
2.  If missing or expired, it generates a unique random email (`anon_xxxx@aahar.com`) and password.
3.  The client registers the user by calling `POST /api/auth/users` passing the project's public `ANON_KEY` as a Bearer token in the `Authorization` header.
4.  The endpoint registers the account (email verification is disabled for this project) and returns a unique user `accessToken` which is persisted locally.

### Flow 2: Image Upload & Analysis
To handle file uploads securely without exposing S3 credentials:
1.  **Request Strategy**: The client calls `POST /api/storage/buckets/meals/upload-strategy` passing the filename and size.
2.  **Upload File**:
    *   If the strategy method is `direct` (local storage), the client makes a `PUT` request to `/api/storage/buckets/meals/objects/{filename}` with a `Multipart/form-data` payload.
    *   If the strategy method is `presigned` (S3), the client appends all signature fields returned in the strategy `fields` object *before* appending the file, and makes a signature-authenticated `POST` request directly to the S3 bucket URL (without passing the client's `Authorization` header).
3.  **Confirm Upload**: If S3-based, the client makes a `POST` request to `confirmUrl` to register the upload.
4.  **Analyze**: The client calls the `/analyze-meal` edge function with `{ image_path, idempotency_key }` forwarding the user `accessToken`.
5.  **Deno S3 Redirect Handling**: Inside the edge function, the image is fetched from the storage backend. To prevent Deno's `fetch()` from forwarding the user's `Authorization` header to AWS S3 (which rejects requests containing both signature params and auth headers), the function first requests the **download strategy** for the key. If presigned, it fetches the file directly from S3 *without* headers.

## 3. Mobile Application Migration & Setup Guide

If migrating from the HTML client to a mobile application (e.g. Kotlin on Android or Swift on iOS), follow these steps to ensure the application flow remains unbroken.

### Step A: Native Authentication Integration
Mobile clients must request `client_type=mobile` during registration or session establishment. This is critical because:
*   **Web Clients** store refresh tokens in HTTP-only cookies and use CSRF tokens.
*   **Mobile Clients** receive the `refreshToken` directly in the JSON response body.

#### 1. Registration / Sign-In Request (Mobile)
```http
POST /api/auth/users?client_type=mobile
Content-Type: application/json
Authorization: Bearer <ANON_KEY>

{
  "email": "user@example.com",
  "password": "securepassword123"
}
```

#### 2. Saving Tokens
The response will return:
```json
{
  "user": { "id": "uuid", "email": "user@example.com" },
  "accessToken": "JWT_ACCESS_TOKEN",
  "refreshToken": "ROTATING_REFRESH_TOKEN"
}
```
*   Save the `accessToken` in memory.
*   Save the `refreshToken` in secure hardware-backed storage (Android **EncryptedSharedPreferences** or iOS **Keychain**). Do not save it in standard plaintext databases.

#### 3. Refreshing Session
When the `accessToken` expires (or returns `401`), call the refresh endpoint to receive a rotated pair:
```http
POST /api/auth/refresh?client_type=mobile
Content-Type: application/json

{
  "refreshToken": "ROTATING_REFRESH_TOKEN"
}
```
Update both the `accessToken` in memory and the `refreshToken` in your secure persistent storage.

---

### Step B: S3 Storage Upload Flow (Mobile)
Mobile applications must implement the multi-step upload strategy to ensure compatibility with both local development disk storage and production S3 backends.

#### 1. Retrieve Upload Strategy
```http
POST /api/storage/buckets/meals/upload-strategy
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "filename": "meal-photo-123.jpg",
  "contentType": "image/jpeg",
  "size": 340200
}
```

#### 2. Execute Multipart Upload
Parse the strategy response:
*   **If `strategy.method == "presigned"` (S3)**:
    Construct a multipart form request to `strategy.uploadUrl`. You **MUST** append fields in the exact order:
    1. Append all key-values returned inside the `strategy.fields` map (e.g. `key`, `AWSAccessKeyId`, `policy`, `signature`, etc.).
    2. Append the binary file data under the key `file` **last**.
    *Warning*: Do not include the `Authorization` header in this call to S3.
*   **If `strategy.method == "direct"` (Local Disk)**:
    Construct a `PUT` request with `multipart/form-data` containing only the `file` field, sent to `strategy.uploadUrl`, passing the `Authorization: Bearer <accessToken>` header.

#### 3. Confirm Upload (If S3)
If `strategy.confirmRequired == true`, immediately send the confirmation request:
```http
POST /api/storage/buckets/meals/objects/meal-photo-123.jpg/confirm-upload
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "size": 340200,
  "contentType": "image/jpeg"
}
```

---

### Step C: Database Queries & Edge Function Invocations
To make direct CRUD operations on database records (e.g. updating profile details or checking logged weights):

*   **API Path**: `https://<appkey>.<region>.insforge.app/api/database/records/{tableName}`
*   **Fetch Filter Format**: Use standard PostgREST format, e.g. `?user_id=eq.{user_uuid}`.
*   **Create/Update Headers**: Include `Prefer: return=representation` to receive the inserted/updated rows back in the response.
*   **Inserting Rows**: The request payload **MUST** always be an array of objects, even when inserting a single record: `[{ "weight_kg": 72.5, "user_id": "uuid" }]`.
*   **Invoke Edge Functions**: Make a `POST` request to `https://<appkey>.function2.insforge.app/{function-slug}` forwarding `Authorization: Bearer <accessToken>` in the headers, passing parameters in the JSON body.

## 4. Deployment & Verification

### Executing Migrations Locally
To initialize or reset the database tables, verify the schema script is committed, and run:
```bash
npx @insforge/cli db import ./schema.sql
```

### Deploying Function Code
If function files under `functions/` are modified, redeploy them via the CLI:
```bash
npx @insforge/cli functions deploy analyze-meal --file ./functions/analyze-meal/index.ts --name "Analyze Meal" --description "Analyze food images for macros using Gemini"

npx @insforge/cli functions deploy coach-chat --file ./functions/coach-chat/index.ts --name "Coach Chat" --description "AI nutrition and macro coach using Gemini"
```
